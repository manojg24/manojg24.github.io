01 — motivation
Why I built this

Coming from 2 years of firmware development at Continental, I worked with UART, CAN, and LIN protocols daily — but always through AUTOSAR BSW layers and vendor HALs. I never had to think about what was happening at the register level.

I built this driver to answer a simple question: what actually happens when a byte travels over a wire? No libraries, no abstractions — just me, a datasheet, and the ATmega328P register map. It forced me to understand baud rate math, interrupt timing, and why a circular buffer is the right data structure for a UART receiver.

02 — architecture
How it works

The driver has two independent data paths — RX and TX — both backed by ring buffers and driven by hardware interrupts.

// RX PATH Laptop terminal │ USB → serial ▼ UDR0 (hardware receives byte) │ USART_RX_vect fires ▼ ISR reads UDR0, checks FE0/DOR0 │ stores in rx_buf[tail++] ▼ RX Ring Buffer [64 bytes] │ main loop polls uart_available() ▼ Command Parser accumulates until \n │ strcmp("led on") / strcmp("led off") ▼ GPIO → PB5 on/off // TX PATH uart_tx_string("Ok\n") │ pushes bytes to tx_buf[tail++] ▼ TX Ring Buffer [64 bytes] │ UDRIE0 enabled ▼ USART_UDRE_vect ISR fires │ writes tx_buf[head++] → UDR0 ▼ Hardware shifts bits out at 9600 baud │ ▼ Laptop terminal prints response

The key insight is that neither path blocks the CPU. RX bytes arrive asynchronously and are stored immediately by the ISR. TX bytes are queued and drained automatically by the UDRE interrupt — main never waits.

03 — implementation
The interesting parts

Baud rate is configured by writing a calculated value to UBRR0. The formula divides the CPU clock by the desired baud rate:

uart.c — baud rate config C 
// UBRR0 = (F_CPU / 16 / BAUD) - 1
// At 16MHz, 9600 baud → UBRR0 = 103
#define UBRR_VAL ((F_CPU / 16 / BAUD) - 1)

void uart_init(void) {
    UBRR0 = UBRR_VAL;                         // set baud rate
    UCSR0B |= (1<<TXEN0)|(1<<RXEN0)|(1<<RXCIE0); // enable TX, RX, RX interrupt
    UCSR0C |= (1<<UCSZ01)|(1<<UCSZ00);        // 8 data bits, 1 stop bit
}

The RX ISR reads the status register before touching UDR0 — important because reading UDR0 clears the error flags:

uart.c — interrupt-driven RX with error handling C 
ISR(USART_RX_vect) {
    uint8_t status = UCSR0A;   // read status FIRST — clears on UDR0 read
    uint8_t data   = UDR0;

    // discard on framing error or data overrun
    if (status & ((1<<FE0) | (1<<DOR0))) return;

    // drop byte if buffer full (overflow protection)
    if ((rx_buf.tail + 1) % BUFFER_SIZE == rx_buf.head) return;

    rx_buf.buffer[rx_buf.tail] = data;
    rx_buf.tail = (rx_buf.tail + 1) % BUFFER_SIZE;
}

Non-blocking TX works by queuing bytes and enabling the UDRE interrupt. The ISR drains the buffer one byte at a time and disables itself when empty:

uart.c — non-blocking TX C 
void uart_tx_byte(uint8_t byte) {
    // spin only if TX buffer is full (rare)
    while ((tx_buf.tail + 1) % BUFFER_SIZE == tx_buf.head);
    tx_buf.buffer[tx_buf.tail] = byte;
    tx_buf.tail = (tx_buf.tail + 1) % BUFFER_SIZE;
    UCSR0B |= (1<<UDRIE0);  // kick the TX ISR
}

ISR(USART_UDRE_vect) {
    if (tx_buf.head != tx_buf.tail) {
        UDR0 = tx_buf.buffer[tx_buf.head];
        tx_buf.head = (tx_buf.head + 1) % BUFFER_SIZE;
    } else {
        UCSR0B &= ~(1<<UDRIE0);  // buffer empty — disable interrupt
    }
}
04 — design decisions
Why I made these choices
Why interrupt-driven RX instead of polling?
Polling means the CPU constantly checks the RXC0 flag — it can't do anything else. With an ISR, the CPU is free and only gets interrupted when a byte actually arrives. At 9600 baud a byte arrives every ~1ms — polling would waste most of that time doing nothing.
Why a circular ring buffer?
The ISR and main loop run at different speeds — the ISR fires on every incoming byte, main reads when it's ready. A ring buffer decouples them cleanly. No dynamic allocation, no shifting, just two pointers wrapping around a fixed array. O(1) read and write.
Why non-blocking TX?
The original blocking TX busy-waited on UDRE0 — the CPU sat idle while the hardware shifted bits out. Non-blocking TX queues the bytes and lets the UDRE interrupt handle transmission, freeing the CPU immediately. In a real system this matters for latency-sensitive tasks.
What would I do differently?
Split into uart.h and uart.c with a clean public API — uart_init(), uart_tx(), uart_available(), uart_rx(). Right now everything is in one file which works but isn't reusable. Also add DMA-driven TX for high-throughput scenarios.
05 — demo

To run it yourself — flash with avr-gcc and avrdude, open a serial terminal at 9600 baud:

terminal bash 
avr-gcc -mmcu=atmega328p -DF_CPU=16000000UL -Os -o main.elf main.c
avr-objcopy -O ihex main.elf main.hex
avrdude -c arduino -p atmega328p -P /dev/cu.usbmodem101 -b 115200 -U flash:w:main.hex
screen /dev/cu.usbmodem101 9600
