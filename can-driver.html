Bare-Metal CAN Bus Driver
on STM32 Nucleo-F446RE

Platform STM32F446RE — ARM Cortex-M4
Language Pure C / arm-none-eabi-gcc
Mode bxCAN loopback, 500 kbps
Libraries None — zero HAL/CMSIS
C STM32F446RE ARM Cortex-M4 CAN bxCAN UART Bare-Metal OpenOCD Linker Script
01 — motivation
Why I built this

At Continental I worked with CAN every day — but always through AUTOSAR's BSW layer. The signals just arrived; the framework handled bit timing, mailboxes, and filtering underneath. I wanted to go one level deeper and understand what AUTOSAR was actually doing for me.

I built this on the STM32F446RE — a real ARM Cortex-M4 chip, the same family used in production automotive ECUs — and configured the bxCAN peripheral directly from registers, no HAL, no CMSIS, no startup files generated by STM32CubeMX. Just the reference manual and raw memory-mapped registers.

It runs in loopback mode — no external transceiver needed. The chip transmits a CAN frame and receives it back internally, which is enough to validate the entire driver: bit timing, mailbox handling, filtering, and frame parsing.

02 — architecture
How it works
// INIT SEQUENCE Power on │ ▼ RCC: enable GPIOA + CAN1 + USART2 clocks │ ▼ CAN init mode — set INRQ, wait for INAK │ ▼ Configure CAN_BTR — prescaler, TS1, TS2 → 500 kbps │ enable LBKM (loopback bit) ▼ Configure filter 0 — 32-bit mask mode, accept all IDs │ ▼ Leave CAN init mode — clear INRQ, wait for INAK clear │ ▼ CAN is live // TX PATH can_tx(id, data, len) │ wait for mailbox 0 empty (TME0) │ write ID → CAN_TI0R │ write length → CAN_TDT0R │ pack 8 bytes → CAN_TDL0R / CAN_TDH0R │ set TXRQ → hardware sends frame ▼ Loopback: TX internally routed to RX // RX PATH can_rx(&id, data) │ check FMP bits in CAN_RF0R — message waiting? │ read ID from CAN_RI0R │ read length from CAN_RDT0R │ unpack 8 bytes from CAN_RDL0R / CAN_RDH0R │ release FIFO — set RFOM0 ▼ UART (PA2) prints result to Mac terminal
03 — implementation
The interesting parts

Bit timing is the first real STM32-specific challenge — the baud rate depends on the actual APB1 clock, which defaults to the internal 16MHz HSI oscillator, not an assumed 45MHz:

main.c — CAN bit timing for 500 kbps C 
// baud rate = APB1_clock / (BRP × (1 + TS1 + TS2))
// at 16MHz HSI: BRP=2, TS1=11, TS2=4 → 2 × 16 = 32 → 500kbps
CAN_BTR = 0;
CAN_BTR |= (1 << 30);   // LBKM — loopback mode
CAN_BTR |= (3 << 20);   // TS2 (register value = actual - 1)
CAN_BTR |= (10 << 16);  // TS1
CAN_BTR |= (1 << 0);    // BRP

Transmission writes the CAN ID, length, and 8 data bytes directly into the mailbox registers, then requests transmission:

main.c — can_tx() C 
void can_tx(uint32_t id, uint8_t* data, uint8_t len) {
    while (!(CAN_TSR & (1<<26)));   // wait — mailbox 0 empty (TME0)

    CAN_TI0R = 0;
    CAN_TI0R |= (id << 21);          // standard 11-bit ID
    CAN_TDT0R = len & 0x0F;          // data length code

    CAN_TDL0R = data[0] | (data[1]<<8) | (data[2]<<16) | (data[3]<<24);
    CAN_TDH0R = data[4] | (data[5]<<8) | (data[6]<<16) | (data[7]<<24);

    CAN_TI0R |= (1<<0);              // TXRQ — request transmission
}

Reception is the mirror image — read instead of write, unpack instead of pack:

main.c — can_rx() C 
uint8_t can_rx(uint32_t* id, uint8_t* data) {
    if (!(CAN_RF0R & 0x03)) return 0;   // FMP — no message waiting

    *id = (CAN_RI0R >> 21) & 0x7FF;
    uint8_t len = CAN_RDT0R & 0x0F;

    data[0] = (CAN_RDL0R >> 0)  & 0xFF;
    data[1] = (CAN_RDL0R >> 8)  & 0xFF;
    data[2] = (CAN_RDL0R >> 16) & 0xFF;
    data[3] = (CAN_RDL0R >> 24) & 0xFF;
    data[4] = (CAN_RDH0R >> 0)  & 0xFF;
    data[5] = (CAN_RDH0R >> 8)  & 0xFF;
    data[6] = (CAN_RDH0R >> 16) & 0xFF;
    data[7] = (CAN_RDH0R >> 24) & 0xFF;

    CAN_RF0R |= (1<<5);   // RFOM0 — release FIFO slot
    return len;
}
04 — the hard fault
Debugging a crash with no debugger output

After adding UART output, the board immediately went into a hard fault — red LED, no serial output, completely unresponsive. No printf, no breakpoint hit, nothing to go on except OpenOCD's halt info.

// root cause

My linker script defined only two entries in the interrupt vector table — the initial stack pointer and the Reset_Handler. But the Cortex-M4 core fetches its NMI handler, HardFault handler, and other exception vectors from fixed offsets immediately following the reset vector (0x08, 0x0C, and onward).

With nothing there, any spurious exception — including one triggered by accessing a peripheral register before its clock was fully stable — caused the core to jump to garbage memory. That triggered a second fault while already in a fault handler, which on Cortex-M4 escalates straight into a lockup state. Hence the red LED with zero output: the chip was stuck in a fault-on-fault condition before a single line of my code even ran reliably.

The fix: pad the vector table with proper stub handlers for at least the core exception vectors (NMI, HardFault, MemManage, BusFault, UsageFault) before Reset_Handler, so any unexpected exception lands somewhere safe instead of unmapped memory.

This was a useful reminder that on bare-metal ARM, the vector table isn't just "where execution starts" — it's the exception dispatch table for the entire core. Skipping entries doesn't just mean "those interrupts won't work," it means any fault that tries to use them corrupts execution silently.

05 — design decisions
Why these choices
Why loopback mode instead of a real CAN transceiver?
No external hardware needed — the bxCAN peripheral routes TX internally back to RX. This validates the entire driver logic — bit timing, mailbox handling, filtering, frame parsing — without needing a second CAN node or transceiver IC. The same driver code works unchanged with a real transceiver wired to CAN_H/CAN_L.
Why a 32-bit mask filter that accepts everything?
The goal was to validate the driver itself, not build a production filtering scheme. Setting the filter mask to 0x00000000 means "don't care about any ID bit" — every frame passes through to FIFO 0. In a real application you'd narrow this to only the IDs your node cares about.
Why no HAL or CMSIS?
Same reasoning as the UART driver — using ST's HAL means calling someone else's abstraction, not understanding the bxCAN peripheral. Direct register access through the reference manual is slower to write but the only way to actually learn what AUTOSAR's CAN driver layer is doing underneath.
What would I add next?
A real transceiver (e.g. TJA1050) to test on an actual two-wire CAN bus instead of loopback. Interrupt-driven RX using CAN_RX0_IRQHandler instead of polling FMP bits. Extended (29-bit) ID support alongside standard IDs.
