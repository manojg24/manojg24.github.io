01 — motivation
Why build malloc from scratch?

In embedded systems, dynamic memory allocation using the standard malloc and free is often a liability. It can fragment memory unpredictably, introduce non-deterministic timing, and depends on OS features that aren't available on bare-metal targets. For safety-critical firmware — device controllers, automotive ECUs, storage systems — you need deterministic behavior and complete control over memory usage.

This project builds a custom allocator on a fixed-size 64 KB static heap with no OS dependencies. Every allocation and free is controlled, measurable, and predictable. The goal was to understand what malloc actually does under the hood — block headers, splitting, coalescing, fragmentation — and build it from first principles in pure C.

03 — how it works
The heap, the header, and the linked list

The entire heap is a statically allocated 64 KB array. It's divided into blocks organized as a singly linked list. Every block — whether free or used — starts with a 12-byte header.

// block header — 12 bytes

size (4 bytes) — total size of this block including the header

is_free (4 bytes) — allocation flag: 1 = free, 0 = used

next (4 bytes) — pointer to the next block in the list

The linked list structure means you can traverse the entire heap by following next pointers from the start. Allocation, splitting, and coalescing all work by walking this list and manipulating headers in place — no external data structures needed.

04 — allocation & freeing
First-fit, splitting, and coalescing
// malloc(size) Start at heap base │ ▼ Walk linked list looking for free block >= requested size │ ├── block too small → skip, move to next │ ├── block exact size → mark USED, return payload pointer │ └── block larger than needed → SPLIT only if leftover >= 12B header + min payload │ block[0..size] → mark USED │ block[size..end] → new FREE block with its own header └── return payload pointer // free(ptr) Mark block as FREE │ ▼ Traverse full list looking for adjacent free blocks │ └── if block[i] FREE and block[i+1] FREE → COALESCE: merge into one larger free block update block[i].size, update block[i].next repeat until no more adjacent free pairs
malloc_free.c — block header and allocation C 
typedef struct Block {
    size_t        size;     // total block size including header
    int           is_free;  // 1 = free, 0 = used
    struct Block* next;    // next block in linked list
} Block;

#define HEAP_SIZE   65536   // 64 KB
#define HEADER_SIZE sizeof(Block)  // 12 bytes

static char heap[HEAP_SIZE];  // static — no OS dependency
static Block* free_list = (Block*)heap;

void* my_malloc(size_t size) {
    Block* curr = free_list;

    while (curr) {
        if (curr->is_free && curr->size >= size + HEADER_SIZE) {
            // split if leftover is large enough for a new block
            if (curr->size >= size + HEADER_SIZE * 2) {
                Block* split = (Block*)((char*)curr + HEADER_SIZE + size);
                split->size    = curr->size - size - HEADER_SIZE;
                split->is_free = 1;
                split->next    = curr->next;
                curr->next     = split;
                curr->size     = size + HEADER_SIZE;
            }
            curr->is_free = 0;
            return (char*)curr + HEADER_SIZE;  // return payload pointer
        }
        curr = curr->next;
    }
    return NULL;  // out of memory
}
malloc_free.c — free with coalescing C 
void my_free(void* ptr) {
    if (!ptr) return;

    Block* block = (Block*)((char*)ptr - HEADER_SIZE);
    block->is_free = 1;

    // coalesce adjacent free blocks
    Block* curr = free_list;
    while (curr && curr->next) {
        if (curr->is_free && curr->next->is_free) {
            // merge curr and curr->next into one block
            curr->size += curr->next->size;
            curr->next  = curr->next->next;
        } else {
            curr = curr->next;
        }
    }
}
05 — design decisions
Why these choices
Why first-fit instead of best-fit?
First-fit stops at the first block large enough for the request. Best-fit scans the entire list to find the smallest sufficient block. For embedded systems, first-fit wins on speed and determinism — it's O(n) in the worst case but exits early in practice. Best-fit produces less fragmentation but its O(n) worst case always hits. For real-time systems, predictable timing matters more than minimal fragmentation.
Why a static heap instead of dynamic growth?
On embedded targets there's no OS to request more memory from. A fixed static array means the memory budget is known at compile time — critical for safety-critical systems where you need to prove the firmware won't exceed available RAM. It also eliminates sbrk() and mmap() dependencies entirely.
Why coalesce on every free?
Without coalescing, repeated alloc/free cycles fragment the heap into tiny unusable blocks. Coalescing on every free keeps the heap healthy — adjacent free blocks are always merged immediately. The cost is a full list traversal on each free, but for a 64KB heap with small block counts this is acceptable and the fragmentation benefit is significant.
Why a 12-byte header?
Size (4B) + is_free flag (4B) + next pointer (4B) = 12 bytes. The size field lets you jump to the next block without following the pointer — useful for coalescing. The next pointer keeps the linked list traversal explicit. On 32-bit embedded targets, 4 bytes per field is natural alignment.
06 — profiling
How performance was measured

A custom profiling tool was written alongside the allocator to measure behavior under stress. It runs 10,000+ randomized allocation and free cycles, tracking allocation latency, peak fragmentation, and memory utilization at each step.

Fragmentation measurement: largest free block / total free memory. A ratio close to 1 means memory is healthy — one large contiguous free region. A ratio close to 0 means heavy fragmentation — many small unusable blocks.

After the stress test, the allocator achieved ~82% memory utilization with ~33% peak fragmentation — meaning coalescing was effective at keeping the heap usable throughout the test.

07 — takeaways
What I learned
//
What malloc actually does
Block headers, linked lists, splitting, coalescing — the standard library malloc implements these same concepts, just with more edge cases and optimizations.
{}
Fragmentation is real
33% peak fragmentation on a simple first-fit allocator shows why embedded systems avoid dynamic allocation. A fragmented heap can fail an allocation even with plenty of total free memory.
~~
Determinism vs efficiency
First-fit trades optimal packing for speed and predictability. In embedded firmware, knowing the worst-case timing matters more than squeezing out the last byte of utilization.
!!
Embedded memory constraints
No OS, no sbrk(), no virtual memory — you work with exactly what you have. Static allocation forces you to think carefully about memory budgets at design time.
