01 — motivation
Why I built this

This was a semester-long project for my Compiler Design course at Texas A&M. The goal was to build a complete compiler from scratch — not just a toy lexer, but the full pipeline from source code to executable machine instructions.

What drew me to this project was understanding what a compiler actually does between the source code you write and the binary that runs. Every optimization, every register decision, every branch — the compiler made those choices. Building it yourself is the only way to understand why.

The two parts I found most interesting were the optimization pipeline — how you can eliminate dead code and propagate constants across an entire program — and graph-coloring register allocation, which turns the abstract problem of "which variable goes in which register" into a graph theory problem.

03 — each stage explained
What happens at every step
Front End
Lexer, Parser, AST

Hand-written lexer tokenizes the source. The parser builds a full AST hierarchy covering integer, float, and boolean types, arithmetic and boolean expressions, if/while/repeat loops, first-class functions, multidimensional arrays, return statements, and built-in I/O. Type checking runs on the AST — enforcing arithmetic rules, float-int coercions, function parameter types, and return type validation.

IR
Three-Address-Code + Control Flow Graph

The AST is lowered to TAC — a simplified intermediate representation where each instruction has at most three operands. Instructions are grouped into BasicBlocks with explicit predecessor and successor lists, forming the CFG. The IR is printable as a DOT graph for debugging. CFG tools handle empty block merging, unreachable block elimination, and branch simplification.

Optimizations
Local + Global Optimization Pipeline

Multiple optimization passes run on the IR. Local passes operate within basic blocks. Global passes (GCP, function inlining) operate across the entire program. A fixpoint loop repeats passes until the IR stops changing. The -max mode runs the full recommended pipeline automatically.

Reg Alloc
Graph-Coloring Register Allocation

Liveness analysis computes which variables are live at each program point. An interference graph is built — two variables interfere if they're both live at the same time and can't share a register. The graph is colored using Chaitin's algorithm: simplify (remove low-degree nodes), color, and spill if coloring fails. Spilled values go to memory locations (M_x). After allocation, silly self-moves (mov R# → R#) are removed.

Code Gen
DLX Machine Code Generation

TAC instructions are translated to DLX machine code — a MIPS-like architecture. Integer ops map to ADD/SUB/MUL/DIV, float ops to fADD/fSUB/fMUL/fDIV. Comparisons use subtract + branch. Float literals are packed using FP16/FP32. Function calls use JSR with return values in R27. Branch offsets are PC-relative. The output is executed by the provided DLX.java simulator.

04 — optimization passes
What each pass does
Flag Optimization What it does
cp Copy Propagation Replaces uses of copied variables with the original
cpp Constant Propagation Replaces variables with known constant values
cf Control-Flow Simplification Eliminates unreachable branches and simplifies jumps
cse Common Subexpression Elimination Reuses previously computed expressions instead of recomputing
dce Dead Code Elimination Removes instructions whose results are never used
cfg CFG Cleanup Removes empty and unreachable blocks from the graph
ofe Orphan Function Elimination Removes functions that are never called
GCP Global Constant Propagation Propagates constants across function boundaries — global scope
inline Function Inlining Replaces small function calls with their bodies — eliminates call overhead
-max Full Pipeline cp → cpp → cf → cse → dce → cfg → ofe → merge → GCP → inlining → DCE → CFG
05 — deep dive
Graph-coloring register allocation — the hardest part

Register allocation is one of the classic hard problems in compiler design. You have an unlimited number of virtual variables in the IR, but only a fixed number of physical registers (R1–R27 in DLX). The question is: which variable goes in which register, and what do you do when you run out?

// how graph coloring works

Step 1 — Liveness analysis: For every point in the program, compute which variables are "live" — meaning they hold a value that will be used later. This requires a backwards dataflow analysis over the CFG.

Step 2 — Interference graph: Two variables interfere if they are both live at the same time — meaning they can't share a register. Build a graph where nodes are variables and edges connect interfering pairs.

Step 3 — Graph coloring: Assign colors (registers) to nodes such that no two adjacent nodes share a color. This is NP-complete in general, so we use Chaitin's heuristic — repeatedly remove the lowest-degree node (it's easiest to color), then color in reverse order.

Step 4 — Spilling: If a node can't be colored (too many neighbors), spill it — store it in memory (M_x) instead of a register. Insert loads and stores around each use.

// after liveness analysis
// a: live at lines 2-3, b: live at 1,3, c: live at 1, d: live at 3, e: live at 4

// interference graph edges: a-b, a-d, b-d, b-e, d-e
// color with 3 registers: a=R1, b=R2, c=R3, d=R4, e=R1 (a is dead)

// DLX output

SUB  R1, R4, R2   // e = d - b (reuse R1, a is dead)
RET  31           // return e in R1
// honest note on SSA

The IR is TAC in an SSA-like form — but true SSA with proper phi-function insertion was not fully implemented. The optimizer and register allocator work on the TAC CFG directly. This contributed to some edge cases in register allocation that caused roughly 20% of private test cases to fail. The core pipeline — parsing, optimization, code generation — works correctly on well-formed programs.

06 — results
What works, what doesn't
What works well
Full front end — lexing, parsing, AST construction, type checking. Complete optimization pipeline including GCP and function inlining. Graph-coloring register allocation on the majority of programs. DLX code generation for integer and float arithmetic, control flow, and function calls. Passed approximately 80% of private test cases.
Known limitations
SSA phi-function insertion is simplified — not fully correct in all cases. This causes some register allocation edge cases to fail, particularly around loop-carried dependencies and complex control flow. The remaining ~20% of test failures trace back to these register allocation issues.
What I would fix
Proper phi-function insertion at CFG join points — this is the foundation SSA is built on and getting it right would fix most of the remaining failures. After that, a more sophisticated spilling heuristic (frequency-based rather than highest-degree) would reduce unnecessary memory traffic.
07 — takeaways
What I learned
//
Compiler pipeline
Every stage — lexer, parser, AST, IR, optimizer, register allocator, code gen — has a precise job. A bug in any one stage propagates through everything below it.
{}
Graph coloring
Register allocation is a graph problem. Liveness analysis, interference graphs, Chaitin's algorithm — classical computer science applied to a real engineering problem.
~~
Dataflow analysis
Liveness, constant propagation, reaching definitions — all solved by iterating equations over the CFG until a fixed point. The same pattern applies to all of them.
!!
IR design matters
The quality of your IR determines how easy optimization and code generation are. SSA makes many analyses trivial. Getting it wrong early costs you everywhere downstream.
