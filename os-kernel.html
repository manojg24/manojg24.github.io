01 — motivation
Why I built this

I took an Operating Systems course as part of my MS program at Texas A&M, and this kernel was the core project. But beyond the curriculum — I wanted to understand what actually happens after a system boots up. At Continental I worked on firmware that ran on ECUs, but there was always a layer of AUTOSAR and BSW sitting between my code and the hardware.

This project stripped all of that away. No OS underneath, no libraries, just C and assembly running directly on x86. I wanted to understand how memory gets organized, how the CPU switches between threads, how a disk driver works at the register level, and how a file system actually stores data. Building it from scratch is the only way to truly know.

The two parts I'm most proud of — the recursive page table lookup and the zombie thread pattern — both solved problems that weren't obvious until I was deep in the implementation.

03 — six modules
Built incrementally, each on top of the last
1
Frame Manager
Physical Memory — 2-bit Bitmap Allocator

Physical memory is divided into 4KB frames. A 2-bit bitmap tracks every frame's state — FREE, USED, HEAD, or INACCESSIBLE. The HEAD state marks the start of a contiguous block so blocks can be released without storing their size. A static pool registry lets the release function find the right pool owner for any physical address. The allocator protects its own bitmap by marking the management frame as INACCESSIBLE.

// key insight: 2 bits per frame instead of 1 — enables contiguous allocation and O(1) release without size parameter
2
Page Table Management
Virtual Memory — Demand Paging + Page Fault Handler

The kernel sets up a two-level x86 page table structure. The first 4MB is direct-mapped — logical address equals physical address — so the kernel always has a stable foundation. Paging is enabled by writing to CR3 (page directory base) and CR0 (enable paging bit). Above 4MB, memory is demand-paged: the page fault handler catches Exception 14, reads the faulting address from CR2, allocates a physical frame from the Process Pool, and maps it in the page table on the fly.

// two pools: Kernel Pool (2MB–4MB) for system structures, Process Pool (above 4MB) for user frames
3
Virtual Memory Management
Recursive Page Tables + Lazy Allocation via VMPools

This is the most technically interesting part. Instead of storing page tables in the small Kernel Pool, the last entry of the Page Directory points back to itself. This creates fixed logical windows (0xFFFFF000 for the Directory, 0xFFC00000 for Tables) that let the fault handler edit page tables without knowing their physical addresses — so tables can live in the larger Process Pool. VMPools add a lazy allocation layer: allocate() just records the intent in a Region list without touching physical memory. The actual frame is mapped only when the CPU touches that address and triggers a fault.

// recursive page table = the most elegant trick in x86 virtual memory — one self-referencing entry gives you a window into the entire page table structure
4
Thread Scheduler
FIFO Scheduler + Zombie Thread Pattern

The scheduler manages thread lifecycle using a linked-list Ready Queue with O(1) enqueue and dequeue via head and tail pointers. When a thread calls yield(), the scheduler saves context, picks the next thread, and dispatches. The hardest problem: a thread cannot delete its own stack while executing the deletion code. Solution — a Zombie Queue. When a thread finishes, it parks itself in the zombie list instead of self-destructing. The next thread's yield() call reclaims zombie memory safely, because it's running on its own stack at that point.

// zombie pattern solves the "can't free your own stack" problem — defer cleanup to the next scheduled thread
5
Disk Device Driver
Non-Blocking Disk I/O — No Busy Waiting

The original SimpleDisk spun in a tight loop waiting for the disk head to seek — wasting 100% of the CPU during mechanical I/O latency. NonBlockingDisk overrides wait_while_busy() to call yield() inside the loop instead. When the disk is seeking, the calling thread moves to the back of the Ready Queue and other threads execute. The disk operations still complete correctly when the thread is rescheduled — just without burning CPU cycles during the wait.

// one line change: while(is_busy()); → while(is_busy()) { yield(); } — turns wasted CPU into useful work
6
File System
Indexed Allocation — Files up to 64KB

The file system organizes disk blocks into a fixed layout: Block 0 stores inodes, Block 1 stores a freelist bitmap, and the rest are data blocks. Basic files are limited to 512 bytes (one block). The extended implementation uses indirect index blocks — each inode points to an Index Block containing 128 pointers to 512-byte data blocks, giving a maximum file size of 64KB. On-demand block allocation in Write() and dirty cache flushing before block switches ensures data integrity. DeleteFile iterates the index block to free all associated data blocks before releasing the inode.

// indirect indexing: inode → index block (128 pointers) → 128 × 512B data blocks = 64KB max file size
04 — deep dives
The two parts I'm most proud of
// recursive page table — the elegant trick

The problem: to edit a page table, you need to know its physical address. But page tables live in virtual memory. You'd need another page table to find them — infinite regress.

The solution: point the last entry (entry 1023) of the Page Directory back to the Page Directory itself. Now the CPU's own address translation hardware gives you a fixed logical window into every page table in the system — 0xFFFFF000 always resolves to the Page Directory, and 0xFFC00000 gives you the base of all page tables. No physical addresses needed. This is what lets page tables live in the large Process Pool instead of the small Kernel Pool.

It's one of those solutions that feels like magic until you trace through the address translation by hand — then it's obvious and beautiful.

// zombie threads — deferred cleanup

The problem: when a thread finishes execution, it needs to free its own stack. But the code that frees the stack is still running on that stack. You can't pull the floor out from under yourself.

The solution: instead of self-destructing, the finished thread calls terminate() which parks it in a Zombie Queue. The next thread's yield() call starts with reclaim_zombies() — it deletes the zombie's memory while safely running on its own stack. The zombie's resources are reclaimed exactly one yield() cycle after the thread finishes. Clean, safe, no leaks.

scheduler.C — yield() with zombie reclamation C 
void Scheduler::yield() {
    // reclaim zombies first — safe because we're on our own stack
    reclaim_zombies();

    // dequeue next thread from head of ready queue — O(1)
    Thread* next = ready_head;
    ready_head = ready_head->next;
    if (!ready_head) ready_tail = nullptr;

    // context switch — saves current, restores next
    Thread::dispatch_to(next);
}

void Scheduler::terminate(Thread* t) {
    // park in zombie queue instead of deleting
    t->next = nullptr;
    if (!zombie_tail) zombie_head = zombie_tail = t;
    else { zombie_tail->next = t; zombie_tail = t; }

    // yield — next thread will reclaim us
    yield();
}
page_table.C — recursive address constants C 
// these magic addresses work because entry 1023 of the
// page directory points back to itself
#define PAGE_DIRECTORY_ADDR  0xFFFFF000  // always resolves to page directory
#define PAGE_TABLES_BASE     0xFFC00000  // base of all page tables

void PageTable::handle_fault(REGS* r) {
    // read faulting address from CR2
    unsigned long fault_addr;
    asm volatile("mov %%cr2, %0" : "=r"(fault_addr));

    // use recursive addresses to check/create page table entry
    unsigned long* pd = (unsigned long*)PAGE_DIRECTORY_ADDR;
    unsigned long pd_idx = fault_addr >> 22;

    if (!(pd[pd_idx] & 0x1)) {
        // page table missing — allocate one from process pool
        unsigned long new_pt = process_mem_pool->get_frames(1) * PAGE_SIZE;
        pd[pd_idx] = new_pt | 0x3;  // present + R/W
    }

    // map physical frame to faulting address
    unsigned long* pt = (unsigned long*)(PAGE_TABLES_BASE + (pd_idx << 12));
    unsigned long pt_idx = (fault_addr >> 12) & 0x3FF;
    pt[pt_idx] = (process_mem_pool->get_frames(1) * PAGE_SIZE) | 0x3;
}
05 — memory layout
How physical memory is organized
// physical address space layout
0x00000 — 0x1FFFFF 2 MB Direct-mapped kernel region
0x200000 — 0x3FFFFF 2 MB Kernel Pool — page tables, system structures
0x400000 — end rest Process Pool — user frames, demand paged

The first 4MB is always direct-mapped — logical address equals physical address. This ensures the kernel never crashes on a page fault in its own code. Everything above 4MB is demand-paged through VMPools — physical frames are only allocated when actually accessed.

06 — challenges
What was hard
Understanding recursive page tables
The recursive trick isn't intuitive — it took tracing through the address translation by hand multiple times before it clicked. Once it did, the elegance of it was clear: you're using the CPU's own MMU hardware as a tool to navigate the page table structure. No extra data structures needed.
The zombie thread problem
This was a class of bug I hadn't encountered before — a thread trying to free its own execution context. The zombie pattern was the solution, but getting the timing right (reclaim at the start of yield, not the end) took careful reasoning about which stack was active at each point.
Debugging without a debugger
Kernel bugs are brutal to debug — a bad pointer dereference just hangs or resets the machine. No printf until you've set up serial output. Learning to reason carefully about what the hardware is doing from first principles, rather than relying on tools, was the biggest skill this project built.
