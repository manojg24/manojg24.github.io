01 — motivation
Why I built this

At Continental I worked on firmware that ran on ECUs — but I never had to think about how that firmware got onto the ECU safely, or what happened if an update went wrong mid-flash. Bootloaders are the first thing that runs on any embedded system, and they're responsible for making sure only valid, uncorrupted firmware ever executes.

I built this project to understand that mechanism from scratch — dual-slot firmware storage, CRC integrity verification, and automatic rollback if the primary slot is invalid. No hardware needed — flash memory is simulated as a file, which mirrors how real bootloaders abstract hardware anyway.

02 — flash memory layout
How the 512KB is organized

The flash is divided into four regions. The bootloader lives at the bottom, two firmware slots sit above it, and a small metadata region at the top tracks which slot is active and stores firmware headers.

// flash.bin — 512 KB simulated flash layout
0x00000 — 0x07FFF 32 KB Bootloader
0x08000 — 0x27FFF 128 KB Slot A — primary firmware
0x28000 — 0x47FFF 128 KB Slot B — fallback firmware
0x48000 — 0x48FFF 4 KB Metadata — headers, active slot flag

Each slot has a firmware header stored in the metadata region encoding a unique ID, payload size, and CRC32 checksum. The bootloader reads these headers before touching the actual firmware image.

03 — architecture
How it works end to end
// BOOT SEQUENCE Power on │ ▼ bootloader.c — entry point │ flash_init() — open flash.bin, initialize to 0xFF ▼ Read firmware headers from metadata region │ Slot A header → unique_id, size, crc32 │ Slot B header → unique_id, size, crc32 ▼ firmware.c — validate Slot A │ null pointer check │ unique_id verification │ size bounds check │ CRC32 over payload ← recomputed, compared to header ▼ Slot A valid? │ YES → boot Slot A │ NO ↓ firmware.c — validate Slot B │ ▼ Slot B valid? │ YES → boot Slot B │ NO ↓ Both slots invalid → HALT system stays in bootloader, safe state

The three source files map directly to three responsibilities — bootloader.c owns control flow, firmware.c owns validation logic, flash.c owns hardware access. This layered approach means the validation logic never touches the file directly — it goes through the flash abstraction layer, exactly like a real embedded system.

04 — file structure
Clean separation of concerns
bootloader/ ├── bootloader.c // entry point, boot sequence, slot selection ├── firmware.c // firmware header validation, CRC32 checks ├── firmware.h // FirmwareHeader struct, validate_firmware() prototype ├── flash.c // flash abstraction — init, read, write via flash.bin ├── flash.h // flash_init(), flash_read(), flash_write() prototypes └── flash.bin // simulated 512KB flash memory file
05 — implementation
The interesting parts

The firmware header struct holds everything the bootloader needs to validate a slot before booting it:

firmware.h — firmware header C 
typedef struct {
    uint32_t unique_id;    // identifies this firmware image
    uint32_t size;         // payload size in bytes
    uint32_t crc32;        // CRC32 checksum of the payload
} FirmwareHeader;

Validation runs four checks in order — if any fail, the slot is rejected immediately:

firmware.c — validate_firmware() C 
int validate_firmware(FirmwareHeader *header, uint8_t *payload) {
    // 1. null pointer check
    if (!header || !payload) return 0;

    // 2. unique ID must match expected value
    if (header->unique_id != EXPECTED_FIRMWARE_ID) return 0;

    // 3. size must be within flash slot bounds
    if (header->size == 0 || header->size > SLOT_SIZE) return 0;

    // 4. recompute CRC32 and compare to header
    uint32_t computed = crc32(payload, header->size);
    if (computed != header->crc32) return 0;

    return 1;  // all checks passed
}

The flash abstraction layer means all reads and writes go through one interface — simulated via a file but identical in API to what a real flash driver would expose:

flash.c — flash abstraction C 
void flash_init(void) {
    // open flash.bin, initialize to 0xFF (erased state)
    flash_file = fopen("flash.bin", "wb+");
    memset(buffer, 0xFF, FLASH_SIZE);
    fwrite(buffer, 1, FLASH_SIZE, flash_file);
}

void flash_read(uint32_t addr, uint8_t *buf, uint32_t len) {
    fseek(flash_file, addr, SEEK_SET);
    fread(buf, 1, len, flash_file);
}

void flash_write(uint32_t addr, uint8_t *buf, uint32_t len) {
    fseek(flash_file, addr, SEEK_SET);
    fwrite(buf, 1, len, flash_file);
}
06 — design decisions
Why I made these choices
Why dual slots instead of single slot?
Single slot means if a firmware update fails mid-write — power loss, corruption — the device is bricked. Dual slots solve this: the bootloader always has a known-good fallback. You write new firmware to the inactive slot, validate it, then switch. If validation fails, the old slot still boots. This is standard in automotive ECUs and any OTA-capable device.
Why CRC32 instead of a simple checksum?
A simple additive checksum misses burst errors — multiple adjacent bits flipping, which is common in flash memory corruption. CRC32 uses polynomial division to detect these patterns reliably. It's not cryptographic — it doesn't protect against intentional tampering — but for detecting accidental corruption in flash, it's the industry standard choice.
Why simulate flash as a file?
No hardware available — but more importantly, it proves the design is hardware-independent. The flash abstraction layer (flash.c) means the bootloader logic never touches the file directly. Swap flash.c for a real flash driver on STM32 or any other MCU and everything above it works unchanged. That's the point of a HAL.
What would I add next?
OTA update via HTTP was planned but not built — that would mean fetching a new firmware image over a network, writing it to the inactive slot, and triggering a reboot. Also cryptographic signature verification (RSA or ECDSA) to protect against intentional tampering, not just accidental corruption.
07 — real world relevance
Where this pattern shows up

This exact design — dual slots, CRC validation, rollback on failure — is used in:

Automotive ECUs — OTA firmware updates on safety-critical systems must never leave the ECU in an unbootable state. Continental and other Tier 1 suppliers use this pattern directly.

IoT devices — ESP32, STM32, and similar chips use dual-slot OTA as the standard update mechanism. The ESP-IDF framework implements exactly this.

Medical devices and aerospace — any system where a failed update cannot be recovered manually needs automatic rollback.
